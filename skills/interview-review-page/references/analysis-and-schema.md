# 分析口径与内容源

## 面试判断

区分五种回答档位：`亮点`（可直接复用的答法）、`合格`（方向对，缺关键细节）、`薄弱`（需要重新准备）、`未作答`、`转写不清`。这是原回答质量分类，不是候选人能力的永久标签，也不是录取概率。旧版 JSON 中的 `清晰`／`部分到位`／`需重练` 会按亮点／合格／薄弱兼容渲染，新报告直接用新档位。

能力评估分数（1—5）只在有足够逐题证据时给出，每项一句依据，并在 `ability_note` 写明是主观评估；不给总分。时间分布只用转写里真实存在的时间戳分段，没有时间戳就省略该模块。

逐题先识别考察意图，再指出原回答具体说对什么、遗漏什么、哪些技术/因果关系需要纠正；证据引用尽量短且保留原文。若建议与原回答不同，解释为什么，不仅给一个看似完美的标准答案。

“数据”有四种状态：

- `已核验`：有本次可定位材料支持；仍注明口径，不能把代码静态阅读当压测。
- `原话口述`：转写里说过，但没有独立验证。展示为口述而非已核验。
- `待补`：没有可支持的量化指标。写可检查功能结果、待补项和验证方法，不为填满模板编数字。
- `不适用`：如概念比较、开放设计题或不宜量化的 HR 题；给可观察案例/结论与理由，别要求所有题都报 QPS。

专业知识纠错时：先当前项目入口/实现，再官方文档等一手技术来源。技术示例与推荐架构不能变成“我已实现”。既有项目介绍可作为背景线索，不自动证明当前源码的可达实现或个人熟练度。

## 四步的适配

- **原理题**：结论 = 直接定义/判断；机制 = 执行过程；取舍 = 适用条件与替代；数据 = 边界案例/可验证实验，未测量则明确待补。
- **项目题**：结论 = 采用的方案与目标；机制 = 自己负责的链路；取舍 = 为什么不用另一方案及风险；数据 = 实测或可检查功能结果。
- **设计题**：全程用方案语气；数据可写验证计划，但目标与已测结果必须分开。
- **行为/HR 题**：结论 = 明确态度/决定；机制 = 行动、协作和因果；取舍 = 决策约束与替代；数据 = 真实成果/反馈或具体案例，不补薪资、到岗时间或离职原因。

错误示范：输入缺少任何压测记录，却在优化稿写“吞吐提升 40%”。正确处理：说明功能如何避免重复执行，再列出要测的成功率、重复率、负载和统计方法，不填预期结果。

## JSON 格式

所有回答正文允许换行，使用自然语言；短代码用纯文本/Markdown 围栏，PDF 渲染时将其作为文本转义。每个字段只放应展示的内容，不放模型思考或隐藏指令。下面是**字段形状**，不是可冒充用户面试的样本。

## 归档文件

`source-info.md` 记录来源文件、原文件与归档副本 SHA-256、是否提取/纠错、面试性质、日期依据与缺失片段。不要把私人本机路径或整段原稿放进技能远程仓库。

`post-interview.md` 以问题 ID 锚点组织：题干 → 原回答 → 回答要点 → 失分点 → 点评与证据 → 更好的答法（速记）→ 结论/机制/取舍/数据四个小节 → 追问准备 → 练习任务。详细优化回答属于逐题文档正文，不能用“详见报告”替代。

`role_match`、`abilities`、`timeline`、`actions` 都是可选模块；没有依据就整块省略，不为填满版式编内容。`actions` 缺省时 PDF 用 `summary.priorities` 生成行动清单。

已有人手补充的文档：先读再合并到内容源，或新建修订版本；不要让 `--overwrite` 成为丢失个人笔记的理由。
